# Kernel ladder, first pass, 2026-08-13


Generated by `scripts/ladder_rung_test.sh`, with each rung prepared by `scripts/ladder_prep_rung.sh`.

Five kernels booted with the corrected flush and the 40-CU unlock, to test
whether the two could coexist, which an earlier revision of this work had
reported as impossible. Each directory is one rung and holds `rung.log` (the
run), `sgemm.log`, `ppl.log`, `tbo.log` (the churn test) and a full `dmesg`.

All five came up at 40 CU with `flush_pasid_uses_kiq=0`, and the sustained
N=4096 GEMM completed with no wrong results and no preemption timeouts on each,
which is what retired the coupling claim.

Note the boot arguments in each `rung.log`: these rungs ran with
`bc250_flush_by_runlist=1`, the original unmap-only behaviour, because the
map-side extension did not exist yet. The churn results here are therefore not
the ones the top-level README quotes for the allocation-reuse defect; those are
in `../ladder-churn-2026-08-16/`, which repeats the ladder with the map side and
adds a same-kernel control.

The perplexity values here use a shorter gate (2 chunks at ctx 1024) than the
campaign elsewhere, so they are not comparable to the 8.9442 reference.
