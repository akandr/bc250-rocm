# Dynamic debug does not reach past the stall, 2026-08-23

Generated by `scripts/netconsole_capture.sh` with `module amdgpu +p` enabled in
`/sys/kernel/debug/dynamic_debug/control`, then a debugfs reset trigger.

## What was tried

The host stalls after a GPU reset and the last line captured has always been
close to the end of the SMU resume. Dynamic debug on the whole amdgpu module was
the obvious way to see further, since it turns on every `pr_debug` in the driver.

## Result: more detail, no more reach

**The capture that backed this section is not the one shipped, found 26 August.**
`netconsole_dyndbg.log` holds boot-time `RDSEED` noise and ends at
`[ 80.019419] about to unload amdgpu`, which belongs to the unload attempt
described further down this page. None of the five lines quoted below is in it,
nor is `GPU reset begin`, and `SetDriverDramAddrHigh` appears nowhere else in
this repository. So the dynamic-debug run's output was not kept and the file
under its name is from the other experiment of the same session.

What survives without it: that the path beyond the SMU resume carries no
`pr_debug` to enable is a property of the amdgpu source rather than of this run,
and the location of the stall is established independently by the resume bisect
in [`../reset-resume-bisect-2026-08-23/`](../reset-resume-bisect-2026-08-23/),
which adds its own prints around the IP-block loop and does ship its capture.
What does not survive is this page's own demonstration.

The extra output is real and lands where expected, inside the SMU resume:

    smu send message: SetDriverDramAddrHigh(4), resp: 0x00000001
    smu send message: SetDriverDramAddrLow(5), resp: 0x00000001
    smu send message: GetEnabledSmuFeatures(61) resp : 0x00000001
    SMU is resumed successfully!
    bc250-40cu-enable: mode=3 se=0 sh=0 ...

and then nothing. The capture stops at the same place as before, this time
without even the clocksource watchdog line that earlier runs ended on.

So the resume path beyond that point contains no debug prints to enable. Dynamic
debug cannot answer this question, which is worth recording so the next person
does not spend the attempt.

## Where the last line actually comes from

`bc250-40cu-enable` is printed inside `gfx_v10_0_get_cu_info()`, reached through
the gfx function table, so the final output is from within the GFX block's
resume rather than from generic device code. Combined with the earlier result
that disabling the unlock entirely does not save the board, the stall is after
SMU and at or beyond GFX resume, with nothing instrumentable in between.

## A test that could not be run

Unloading and reloading the driver would separate "re-initialising this GPU is
broken" from "the reset path specifically is broken". It could not be done:
`modprobe -r amdgpu` fails with `Module amdgpu is in use`, since the display is
bound to it, and `rmmod_rc=1` confirms nothing happened. The board surviving that
attempt is not evidence of anything, and is recorded as untestable rather than as
a negative result.

Doing it properly needs the display unbound first, or a boot with the display
disabled, which is a heavier setup than this cycle warranted.

## Honest assessment

This cycle narrowed the location slightly and closed off one instrument. It did
not produce a finding of the kind the previous cycles did.

## One capture

One triggered reset. The conclusion drawn is narrow, that the path beyond the SMU
resume carries no `pr_debug` to enable and so this instrument is exhausted, and
that part is a property of the source rather than of the run. What is one sample
is the claim about where the output stops.
