# Honest resets, the recovery default, and a gfx10 per-queue reset, 2026-09-15

Generated by [`scripts/honest_reset_test.sh`](../../scripts/honest_reset_test.sh), kernel 7.1.8,
module from [`scripts/apply_tlb_reset_experiments.py`](../../scripts/apply_tlb_reset_experiments.py)
plus [`scripts/apply_gfx10_queue_reset.py`](../../scripts/apply_gfx10_queue_reset.py), front-page
configuration **except** `amdgpu.gpu_recovery=0`, which was removed from the command line for the
whole run so the driver default (-1) applied, and put back at the end (`cmdline_before.txt`,
`cmdline_after.txt`). Every trial starts from its own boot, with the boot id checked, and is
captured over netconsole.

These are the board tests for the two patches in
[`../../patches/amdgpu/`](../../patches/amdgpu/). The experiment module
implements patch 1 as a reorder of the same checks rather than a removal of the early return; for
this chip the two are equivalent.

## A. The recovery default

`log`, `A_probe.txt`. With `gpu_recovery=-1` the module logs `GPU recovery disabled.` twice at
boot, at 6.4 s, when `amdgpu_get_soft_full_reset_mask()` asks the recovery guard while setting up
the reset-mask attributes. Upstream, the RAS early return answers that call before the per-ASIC
list is reached and nothing is logged. The explicit probe in this section did not run, because the
device pointer it needs is only captured by the experimental flush helper, which was idle; section
C exercises the same guard on the path that matters instead.

## B. A reset with no implementation, failing instead of pretending

`B*_mode*.{netconsole.log,dmesg.txt,trigger.txt}`. `amdgpu.bc250_honest_reset=1`, reset requested
by reading `amdgpu_gpu_recover` in debugfs from an idle GPU.

| trial | method | kernel | host | GPU job afterwards |
|---|---|---|---|---|
| B1 | MODE1 (default) | `PSP has no mode1_reset for this ASIC`, `ASIC reset failed with error, -95` | alive | runs |
| B2 | MODE1 | same | alive | runs |
| B3 | MODE2 | `Mode2 reset failed!`, `-95` | alive | runs |
| B4 | MODE2 | same | alive | runs |

Four of four, against a host hang on every deliberate reset recorded before this
([`../reset-path-2026-08-24/`](../reset-path-2026-08-24/),
[`../reset-kiq-repeat-2026-08-24/`](../reset-kiq-repeat-2026-08-24/),
[`../reset-smu-gc-2026-09-14/`](../reset-smu-gc-2026-09-14/)). The smoke job is a short 1.5B
`llama-bench`, run twice after the failed reset.

Two caveats. First, every reboot after a failed reset stalled in shutdown with ssh still answering,
four of four, and needed a power cycle. On failure `amdgpu_device_gpu_recover()` skips both the
scheduler resume and the GPU resume, so the kernel's own DRM ring schedulers stay halted; that is
the likely reason, not a verified one. Second, `amdgpu_device_mode1_reset()` clears bus mastering
before calling the reset and the failure path does not set it again, yet compute works afterwards.
Why is not established. So the failed reset leaves a machine that keeps computing and must be
power-cycled to reboot, which is still far better than the hung host it replaces, but it is not a
clean recovery.

## C. Per-queue reset on gfx10

`C*_queue_reset*.{dmesg.txt,trigger.txt,netconsole.log}`. The trigger is the PASID-filtered runlist
rebuild under a `--no-mmap` perplexity load, which puts a queue into the preemption-failed state
([`../tlb-alt-2026-09-15/`](../tlb-alt-2026-09-15/), round 4). A long dispatch alone does not: an
endless kernel ([`../../patches/hang_probe.c`](../../patches/hang_probe.c)) was preempted cleanly by
the scheduler and a second process ran at full speed beside it.

| trial | `bc250_queue_reset` | preemption failures | queue reset lines | `GPU recovery disabled.` | GPU job afterwards | host |
|---|---|---|---|---|---|---|
| C1 | 0 (stubs) | 66 | 0 | 69 | fails | alive |
| C2 | 1 (port) | 66 | 3 | 69 | fails | alive |
| C3 | 0 (stubs) | 66 | 0 | 69 | fails | alive |
| C4 | 1 (port) | 66 | 3 | 69 | fails | alive |

C1 and C3 are the section-A result on the path that matters. With the gpu_recovery default, every full
reset KFD requested after the preemption failures was refused by the guard, 69 times, and the host
survived. Upstream at the same default attempts the no-op reset instead, which hung the host on
all three KFD-path trials of [`../reset-path-2026-08-24/`](../reset-path-2026-08-24/).

C2 and C4 show the port runs and does not work on this part, identically both times. `SPI_COMPUTE_QUEUE_RESET` left the queue
active for the whole wait, the pipe reset through `CP_MEC_CNTL` did not deactivate it either, and
the GPU stayed unusable:

    BC250QRESET attempting queue reset pipe 0 queue 2
    BC250QRESET queue still active, attempting pipe reset pipe 0
    BC250QRESET pipe 0 queue 2 failed (pipe reset)

Whether the MEC firmware on this chip ignores those registers under hardware scheduling, or needs a
sequence gfx9 does not, is not known.

The identical counts across trials (66 and 69 every time) reflect a fixed trigger: the load runs to
the same 120 s timeout and the driver retries on a fixed interval.

## What this changes

- Patch 1 does what it says on the path that kills the board. At the driver default it turned every
  KFD full-reset request into a refusal and the host survived, four trials of four in section C.
  Section B does not bear on it, since the debugfs trigger bypasses the guard.
- Patch 2 turns a deliberate reset from a hung host into a failed reset on a working machine, four
  of four, at the cost of a reboot that needs a power cycle.
- Neither makes a faulted GPU usable again. A per-queue reset in the gfx9 style does not either, on
  this part. The remaining recovery for a real fault is still a reboot; what changes is that the
  host stays up to perform it, without having to know about `gpu_recovery=0`.
