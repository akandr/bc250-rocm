# Function-tracer captures of the wedge


Generated by `scripts/ftrace_alloc_reuse_window.sh`.

`wedge_eviction_stack.txt` is the stack that identified what the wedge actually
is. Captured on a wedging run while the process was hung mid-dispatch, not
exiting, it shows the path

    evict_process_queues_nocpsch <- kgd2kfd_quiesce_mm <- svm_range_evict
      <- svm_range_cpu_invalidate_pagetables <- __mmu_notifier_invalidate_range_start
      <- __split_huge_pmd <- __x64_sys_munmap

so the trigger is the process's own `munmap`, and the timeout is a queue
eviction whose MEC preemption does not complete rather than a dispatch failing
on its own. The file includes the recipe to reproduce it.

`eviction_profile_and_ordering.txt` counts how often that path runs and in what
order, which is where the observation comes from that the runtime issues a
couple of hundred `munmap` calls over a run from code-object and module
management, roughly constant rather than scaling per GEMM.

Both were captured under `amdgpu.sched_policy=2`, which is the configuration the
`nocpsch` path belongs to. That is not incidental: the wedge is now known to be
specific to that setting.
