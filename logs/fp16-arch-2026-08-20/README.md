**The zeroed fp16 GEMM disappears when the board is driven as gfx1010.** This is
the first thing other than switching compute type that makes it go away, and it
moves the suspicion from "the fp16 path" to "the gfx1013 kernels".

Seven hypotheses had been eliminated for this defect and all of them were tested
against the same library, the locally built gfx1013 rocBLAS, which had never been
varied. Varying it needs a llama.cpp carrying gfx1010 code as well, so one was
built into a separate directory, leaving the measured binary alone.

8B at context 2048 over two chunks, two rounds of each cell:

| device presents as | rocBLAS servicing the GEMMs | f32 compute | f16 compute |
|---|---|---|---|
| gfx1013 | native gfx1013 build | 9.0975, 9.0975 | **17.3015, 13.9642** |
| gfx1010 (override) | system, real gfx1010 objects | 9.0975, 9.0975 | **9.1117, 9.1117** |

Under the override the fp16 arm is correct *and* bit-identical across runs. The
small gap from the f32 value, 9.1117 against 9.0975, is ordinary half-precision
arithmetic rather than the defect: when the defect fires on this model and
context it produces something in the mid teens to low twenties, not 9.11.

That range used to read "14 to 23", and a correction on 25 August replaced it
with "13.9642 to 21.4429, and no reading of 23 exists". That correction was wrong
in both directions and is withdrawn here the same day. Pooling every wrong
reading on record for the 8B at context 2048 over two chunks gives ten distinct
values from 11.5415 to 23.4547, so 23 does exist, in
[`../fp16-library-2026-08-20/`](../fp16-library-2026-08-20/), and the floor is
lower than either version said. The original "14 to 23" had the top right.
Split by binary, since the two are not one series. On the ordinary gfx1013-only
build the wrong readings run 13.9642 to 23.4547; on the dual-architecture build
this page and [`../fp16-arch-2026-08-22/`](../fp16-arch-2026-08-22/) use, 11.5415
to 18.2958. The point the sentence is making survives every version of the range:
every wrong reading is at least half again the correct answer, and 9.1117 is
0.16 percent from it.

**The obvious objection, and why it does not apply.** This repository documents
elsewhere that running a gfx1013-built binary under
`HSA_OVERRIDE_GFX_VERSION=10.1.0` makes its kernels silently do nothing: the code
object no longer matches, the launch is skipped, the output buffer keeps whatever
it held, and no error is raised anywhere. A result of "the defect disappeared
under the override" is exactly what that failure would look like. It is not what
happened here, for two reasons. The binary used is built for both gfx1010 and
gfx1013, so there is a matching code object either way. And the perplexity under
the override is 9.1117 against an f32 reference of 9.0975, a correct answer to
within ordinary half-precision arithmetic. Kernels that had been skipped would
leave the computation unperformed and produce nonsense, not a value within 0.16
percent of the reference. The correctness of the number is the evidence that the
work was done.

**What this does not establish.** The override changes two things at once, the
device identity and the library, so the two are not separated. The cell that
would separate them, gfx1010 identity with the native library on the path, is not
runnable: the native build's Tensile library directory contains gfx1013 code
only, so under a gfx1010 identity it has nothing to dispatch and both compute
types fail. The complementary cell, gfx1013 with the system library, aborts with
`CUBLAS_STATUS_INTERNAL_ERROR`, which is why the native build exists at all. Both
blocked cells are recorded rather than left as gaps.

**What it does establish.** The defect is not inherent to llama.cpp's fp16 cuBLAS
path, because that same path through the same source runs correctly and
repeatably when a different set of code objects services it. Whatever is wrong is
specific to the gfx1013 configuration, and the most likely single suspect is now
the fp16 GEMM kernels in the native gfx1013 Tensile build, which is a much
narrower target than anything the previous seven eliminations produced.
