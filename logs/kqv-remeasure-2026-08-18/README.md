Re-measurement of the KQV-precision figures, the second set the figure audit
found cited with no surviving log.

Configuration taken from the harness that produced the originals rather than
guessed: qwen2.5-1.5B Q4_K_M, ctx 4096, chunks 2, `-fa off`, with
`GGML_CUDA_NO_VMM=1`. An earlier attempt at this used chunks 8 and therefore
compared nothing, since perplexity over a different amount of text is a
different quantity.

| arm | cited | measured |
|---|---|---|
| patch removed, `-fa off`, no compute-type variable | 276.29 | 4199.41 |
| patch removed, `-fa off`, `COMPUTE_TYPE=f32` | 11.0631 | 11.0631 |
| patch removed, `-fa on`, `COMPUTE_TYPE=f32` | 11.0521 | 11.0521 |
| patch restored, `-fa off`, no variable | - | 11.0631 |
| patch restored, `-fa on` | - | 11.0521 |
| Vulkan reference | 11.0279 | 11.0468 |

The two workaround figures reproduce to four decimals, and the patch itself is
confirmed by the restored rows: with the line back, the arm that read 4199
reads 11.0631.

The corrupted figure does not reproduce as a value, and that is the finding
rather than a failure. Running the same arm without `GGML_CUDA_NO_VMM` gives
624.13 instead of 4199.41, so the corrupted magnitude spans more than an order
of magnitude across three observations (276.29 recorded earlier, 624.13 and
4199.41 here) while the correct arms are bit-identical. Quoting 276.29 as though
it were a property of the defect was misleading; what is stable is that the
defect is catastrophic, not how catastrophic.

`GGML_CUDA_NO_VMM` makes no difference to any correct arm (11.0631 either way),
so that constant is inert for the conclusion.

The Vulkan reference sits 0.17 percent from the cited value, which is a build
difference: the original used a separate Vulkan tree and this used the current
one.
