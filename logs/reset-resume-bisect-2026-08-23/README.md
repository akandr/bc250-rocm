# The stall is inside the GFX block's resume, which never returns, 2026-08-23

Generated by `scripts/resume_bisect_probe.sh`, which adds a pair of prints around
the IP-block resume loop in `amdgpu_device_ip_resume_phase2()`, built and
installed with `scripts/install_probe_module.sh`, then triggered through debugfs
and captured over netconsole.

## Why instrumentation was needed

The host stalls after a GPU reset. Every earlier capture ended at the same place
with nothing to say why, and the two obvious suspects were cleared: the reset
method, MODE1 and MODE2 alike, and the 40-CU unlock, which the board dies without.
Dynamic debug reaches into the SMU resume and no further, because the path beyond
has no `pr_debug` to enable. The only remaining route was to add prints.

## Result

    BC250RESUME phase2 entering block 4 <smu>
    SMU is resumed successfully!
    BC250RESUME phase2 block 4 <smu> returned 0
    BC250RESUME phase2 entering block 6 <gfx_v10_0>
    bc250-40cu-enable: mode=3 se=0 sh=0 ...
    bc250-40cu-enable: mode=3 se=0 sh=1 ...
    bc250-40cu-enable: mode=3 se=1 sh=0 ...
    bc250-40cu-enable: mode=3 se=1 sh=1 ...
    clocksource: Watchdog remote CPU 10 read timed out

The SMU block is entered, resumes, and **returns 0**. The GFX block is then
entered and **never returns**: there is no matching "block 6 <gfx_v10_0>
returned" line, and no "phase2 complete". The host stalls with the call
outstanding.

So the stall is not merely "after SMU" as previously recorded. It is inside
`gfx_v10_0`'s resume callback, which does not come back.

## What that rules in and out

The 40-CU unlock prints from `gfx_v10_0_get_cu_info()` during that callback, and
it is the last thing heard. But the unlock is already cleared as the cause:
booting at `bc250_cc_write_mode=0`, with no unlock lines at all, the board dies
the same way. So the hang is elsewhere in the GFX resume, after or independent of
the shader-array configuration.

That is consistent with everything else known about this board. The compute
queue, the CP and its preemption behaviour are where this hardware has misbehaved
since July, and a GFX resume that never returns sits squarely in that territory.

## The probe

Two `dev_warn` calls around `amdgpu_ip_block_resume()` in the phase-2 loop, plus
one after the loop. They fire only during a reset, which under
`amdgpu.gpu_recovery=0` does not happen in normal operation, so the probe is
inert in ordinary use. The patch is kept as a script rather than left installed;
the board was returned to its standard module afterwards.

## One capture

This is one triggered reset, not a repeated measurement. The claim it supports,
that the GFX block's resume callback is entered and never returns, is a claim
about which line was the last to arrive over a lossy UDP transport, so a dropped
packet would look the same. Whether the stopping point is stable across identical
runs is tested in [`../reset-kiq-repeat-2026-08-24/`](../reset-kiq-repeat-2026-08-24/),
which exists because a different single capture on this same path was read as a
mechanism and was not one.
