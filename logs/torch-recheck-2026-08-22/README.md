# PyTorch training, re-checked on the current configuration, 2026-08-22

Generated by running `patches/pytorch/torch_train.py` directly.

The 50-step training loop from `patches/pytorch/torch_train.py`, run on the
native gfx1013 build with the fault hunt stopped. `state.txt` records the
configuration: kernel 7.1.8, navi12 SDMA microcode, `amdgpu.gpu_recovery=0`.

## Why

The last check of this is from 19 August, before the microcode substitution, the
kernel change and the recovery parameter. Training on the GPU is one of the two
headline capabilities this repository claims, so it should be shown to still work
on the configuration currently recommended rather than on the one it was measured
against.

The GPU side is identical. The CPU reference is about 9 percent slower this time,
which is host-side variation and not a statement about the GPU, but it is
reported rather than dropped because the CPU time is quoted in `INVESTIGATION.md`
alongside the GPU one, so a reader comparing them needs to know it moved. No
speedup ratio is stated anywhere; the two times are given raw and the comparison
is left to the reader, which this note used to describe as a quoted ratio.

The failing built-in verdict is the documented one: the script compares
parameters with a 1e-3 threshold and fifty steps of accumulated floating-point
difference between two backends exceeds it, while the losses stay within
1.8e-05 of each other throughout.
