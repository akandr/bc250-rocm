Does the debug instrumentation in the working tree affect the numbers this work
quotes? No, and if anything it is faster.

The 8B decode rate read lower than the campaign of 2026-08-12 and the working
tree had since acquired instrumentation for the fp16 and allocation-reuse
investigations, including `getenv()` calls inside the CUDA memory pool's alloc
and free paths. Those run per pool operation, which decode does per token, so it
was a plausible cause of a decode-only change with prefill flat. It is not.

A clean tree was cloned at the campaign commit (7ba604f), given only the three
shipped patches, and built; both binaries were then measured in the same boot:

| build | 8B pp512 | 8B tg64 | 1.5B pp512 | 1.5B tg64 |
|---|---|---|---|---|
| clean, three patches only | 241.42, 241.84 | 36.40, 36.66 | 807.60 | 113.72 |
| instrumented working tree | 242.26, 242.81 | 38.15, 38.34 | 807.40 | 113.51 |
| campaign, 2026-08-12 | 241.01 | 39.20 | 806 | 113.5 |

The small model reproduces the campaign closely in both builds, so the campaign
is reproducible. The 8B does not separate the builds in the direction the
hypothesis needed, and pooling all eleven independent invocations of that
measurement on record gives mean 37.34, sd 1.20, range 35.40 to 39.20. The
campaign's 39.20 is 1.6 standard deviations above that mean, an ordinary sample.
There was no regression.

The useful residue: `llama-bench` reports an error bar computed across
repetitions within one invocation, and for this model its median is 0.43 while
the across-invocation spread is 1.20. Reported bars understate the real
uncertainty by roughly three times, which is worth knowing before reading any
single-invocation rate in this repository as exact.
