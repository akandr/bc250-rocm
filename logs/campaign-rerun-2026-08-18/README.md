The five-model campaign repeated on the current stack.

The figures quoted throughout the write-up came from the campaign of
2026-08-12. Since then the patch scripts were corrected, the map-side runlist
flush was added, the kernel moved and the library recipe settled, and nothing
had re-measured the most-cited data in the document. This repeats the HIP arms.

Correctness is unchanged: every perplexity gate returns its established value
(8B 9.0975, deepseek-14B 5.9756, and the others consistent with their earlier
readings). Throughput is unchanged within about one percent on four of the five
models.

The 8B looked like an exception and is not. Its decode rate read 35.4 to 36.3
here against 39.20 in the campaign, which was chased through two hypotheses,
both wrong. The map-side runlist flush was ruled out by toggling it live
(`../flush-cost-2026-08-18/`). The debug instrumentation added to the memory
pool's hot path since the campaign was ruled out by building a clean tree at the
campaign commit with only the three shipped patches: the clean build reads 36.40
and 36.66 against the instrumented build's 38.15 and 38.34 in the same boot, so
if anything the instrumented one is faster (`../clean-build-2026-08-18/`).

Pooling every independent invocation of this measurement on record gives mean
37.34, sd 1.20, range 35.40 to 39.20 over eleven runs. The campaign's 39.20 sits
1.6 standard deviations above that mean, which is an ordinary sample rather than
a different regime. There was no regression to explain.

What the chase did surface is worth more than the non-result. `llama-bench`
prints an error bar computed across repetitions inside one invocation, and for
this model that bar has a median of 0.43 while the spread across invocations is
1.20, about three times larger. The campaign's own `39.20 +/- 0.17` is a good
example of a figure that looks far more precise than it is.

The small model reproduces the campaign closely in both builds (pp512 807.60 and
807.40 against 806, tg64 113.72 and 113.51 against 113.5), so the campaign
itself is reproducible; only the noisiest model looked otherwise.

One arm of this re-run tested nothing and is reported so it is not mistaken for
a result: `GGML_CUDA_FORCE_CUBLAS` is a compile-time `#ifdef` in this version,
not an environment variable, so setting it in the harness had no effect and the
"forced-BLAS" figure here is just the default path measured a second time. The
936 t/s figure in the write-up came from a build compiled with that macro and is
not re-verified by this run.
