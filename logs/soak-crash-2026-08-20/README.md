# The alternating-SDMA soak, and the crash that ended it, 2026-08-20

Generated by `scripts/soak_sdma_alternating.sh`. The soak was the outstanding
item from the SDMA microcode substitution: every endurance result in this
repository had been taken with `HSA_ENABLE_SDMA=0`, so nothing long-running had
covered the configuration the recipe now recommends.

## The soak itself

253 rounds over eight hours, SDMA alternated on and off round by round, each
round a 2048-token prefill, a perplexity gate, and an allocation-churn sweep.

| quantity | value |
|---|---|
| rounds completed | 253 |
| distinct perplexity values | 1, `8.9442` on every round |
| prefill range | 661.49 to 663.05 t/s |
| allocation-churn failures | 0 |
| peak edge temperature | 67 C |

The gate value is bit-identical on all 253 rounds with SDMA alternating beneath
it, which is the result the soak was run to get.

## The crash

Round 254 took the board down. It was an SDMA-enabled round, and it failed five
seconds in, during the prefill benchmark. The kernel trail is complete and the
order matters:

    22:14:48  [gfxhub] page fault, vmid 8, pasid 2460, address 0x00007fa800005000
              client TCP (0x8), PERMISSION_FAULTS 0x5, MORE_FAULTS 0x1, three times
    22:14:52  Queue preemption failed for queue with doorbell_id: 80004018
    22:14:52  BC-250: runlist rebuild flush failed (-62)
    22:14:52  GPU reset begin!. Source: 4
    22:14:52  The cp might be in an unrecoverable state due to an unsuccessful
              queues preemption
    22:14:52  sq_intr: error, se 1, ..., err_type 2
    22:14:52  llama-bench terminated abnormally with signal 7/BUS

Then the board rebooted on its own.

## What this settles

The host-side SIGBUS was carried in the write-up as an open observation: seen
once in about twelve runs, not reproduced in a deliberate repeat, with no GPU
fault accompanying it. It has now reproduced, and it is not a separate defect.
It is the last link of a chain. A GPU page fault leads to a queue preemption
that times out, which makes the runlist rebuild this repository's own patch
installs return -62, which triggers a GPU reset, and the reset takes the
process's AQL queue mapping away underneath a store that is already in flight.
The faulting frame is `rocr::AMD::AqlQueue::StoreRelaxed`, reached through
`ggml_cuda_op_add` inside graph evaluation. SIGBUS rather than SIGSEGV was
already noted in the write-up as suggesting a mapping that exists but cannot be
backed, and that reading turns out to be exactly right.

## A methods correction this forces

The earlier observation was recorded as a SIGBUS "with dmesg clean". That was
never evidence. When the board reboots, `dmesg` reports the boot that comes
after, so a fault from the boot that crashed is invisible to it by construction.
The evidence lives in `journalctl -b -1`, which is where the trail above comes
from. Every place this work has said "no fault in dmesg" about a run that ended
in a reboot was reading an empty buffer and reporting it as a clean result.
That is a stronger version of the runtime-versus-kernel blind spot already
recorded in `deep-decode-faults-2026-08-20/`, and it has the same fix: name the
instrument, and check that the instrument could have seen the thing.

## What it does not settle

Whether SDMA is implicated. The failing round had SDMA enabled, but so did
about 127 rounds that passed, so the crash is not evidence against the
microcode substitution. What can be said is narrower: one hard failure in 254
rounds of sustained mixed load, and the failure mode is the same
preemption-timeout family that the compute-queue defect has shown since July,
now observed reaching all the way to a reboot.
