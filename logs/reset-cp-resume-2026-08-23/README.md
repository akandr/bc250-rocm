# The reset stall is in the Command Processor resume, 2026-08-23

Generated by `scripts/gfx_resume_bisect.sh`, which adds prints around the three
main steps of `gfx_v10_0_hw_init()`, built and installed with
`scripts/install_probe_module.sh`, triggered through debugfs and captured over
netconsole.

## Result

    GPU reset begin!. Source:  5
    SMU is resuming...
    SMU is resumed successfully!
    BC250GFX before constants_init
    bc250-40cu-enable: mode=3 se=0 sh=0 CC=0xfff80000->0xffe00000 SPI=0x0000001f->0x0000001f
    bc250-40cu-enable: ... (three more, one per shader array)
    BC250GFX after constants_init, before rlc_resume
    BC250GFX rlc_resume returned 0
    BC250GFX before cp_resume
    clocksource: Watchdog remote CPU 4 read timed out

`gfx_v10_0_constants_init()` completes, and the 40-CU unlock prints from inside
it, which is why that was always the last line before. `gfx_v10_0_rlc_resume()`
returns 0. `gfx_v10_0_cp_resume()` is entered and never returns.

So the stall is in the Command Processor resume.

## How the resume lines are told from boot lines

The unlock prints at boot as well, so the two must not be confused. At boot the
shader-array register transitions `SPI=0x00000007->0x0000001f`, from 24 CUs to
40. On resume it reads `SPI=0x0000001f->0x0000001f`, already at 40. The lines
above are the resume form. An earlier attempt at this run mistook boot-time lines
from the journal for resume output, which is what the distinction guards against.

## The instrument was verified before it was trusted

The first attempt captured two lines and no reset output at all, because
netconsole had been armed while the board was still finishing its boot. Rather
than read that as a result, the run was repeated with a live check: a marker
written to `/dev/kmsg` and confirmed to arrive at the listener before triggering
anything. The trace above is from the verified run.

## What it connects to, and what that is worth

The CP is where this board has misbehaved since July: `cp queue preemption time
out`, the compute-queue defect that made Mesa disable the gfx1013 compute queue,
and the preemption failure that precedes the runlist rebuild returning -62.
A CP resume that never returns is in the same component.

That is suggestive and no more. Sharing a component is not sharing a root cause,
and nothing here shows these are one defect rather than several in the same
place. It is recorded as a connection worth following, not as a conclusion.

This page's own result still stands and was narrowed rather than overturned:
inside `cp_resume` the stall is in the KIQ resume
([`../reset-cp-bisect-2026-08-23/`](../reset-cp-bisect-2026-08-23/)), and within
that it is not any fixed instruction but the first GC register access after the
reset, whichever it happens to be
([`../reset-path-2026-08-24/`](../reset-path-2026-08-24/)).
