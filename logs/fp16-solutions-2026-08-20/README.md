Exercising every Tensile solution rocBLAS would consider for the failing shape,
to see whether one of them is the bad kernel. None is, and the defect does not
appear standalone even when all of them are tried.

Since the defect vanishes when the board is driven as gfx1010, the gfx1013
Tensile kernels are the narrowest suspect. rocBLAS can enumerate the solutions it
considers for a problem and run a chosen one, so the exact shape llama.cpp fails
on can be pushed through each in turn. Shape taken from the dispatch trace rather
than guessed: `gemm_ex`, transA=T transB=N, M=1024 N=512 K=4096, all operands and
compute type `f16_r`, alpha 1, beta 0.

| compute type | solutions offered | producing zeros | flagged by the 5 percent check |
|---|---|---|---|
| f16_r | 6 | 0 | all 6, identically |
| f32_r | 12 | 0 | none |

**No solution produces zeros.** Three repetitions of each of the six, with the
destination pre-filled with `0xFF` so a zeroed result would be unmistakable, and
none appeared. The defect needs the running model, and this is a stronger
statement of that than before: earlier standalone attempts used whichever
solution rocBLAS picked by default, whereas this exercises every candidate.

**All six f16 solutions agree exactly**, at 0.1148 worst relative error on
sampled elements against a CPU reference. That is not a defect and the
uniformity is the giveaway: the same figure from six different kernels is
arithmetic, not a bug. The f32 arm confirms it, with 12 solutions and none over
the threshold. The 5 percent check was simply miscalibrated for half-precision
accumulation over 4096 terms.

That accumulation figure is worth keeping for its own sake. Roughly 11 percent
relative error on an fp16-accumulated K=4096 product is the same arithmetic that
makes llama.cpp's KQV precision patch necessary on this hardware.
