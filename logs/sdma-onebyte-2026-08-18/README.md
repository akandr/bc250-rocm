The single-variable version of the SDMA localisation, what it actually shows,
and a first reading of it that was wrong.

The write-up localised the SDMA failure to the submission end because the KFD
queue descriptor never advances during a hang, against a control showing
descriptors changing during real work. That control was a different workload, so
the comparison varied the workload as well as the hang. Every conclusion this
work has had to withdraw had that shape, which is why the claim was flagged as
the most likely next retraction and tested rather than trusted.

**The measurement.** Arms differ by one byte, through the same binary, with the
queue kept busy for the whole sampling window:

| arm | size | copies completed | SDMA queue present | descriptor changes |
|---|---|---|---|---|
| below_1 | 16384 | 1652160 | no | (compute queue only) |
| above_1 | 16385 | hangs on first copy | yes | none, byte-identical |
| above_2 | 16385 | hangs on first copy | yes | none, byte-identical |
| below_2 | 16384 | 1693568 | no | (compute queue only) |
| control, SDMA disabled | 16385 | 576960 | no | not sampled |

**The wrong reading, corrected.** A first pass counted changed lines between
samples and reported that the descriptor tracks live work at 16384 and is frozen
at 16385. That is misleading. Below the threshold ROCclr uses a blit compute
kernel and **no SDMA queue is created at all**, so the descriptor that changed
was a compute queue doing blit work. The two arms do not compare the same queue,
and on this board no matched positive control is possible, because there is no
size at which an SDMA copy works.

**What the descriptor does show.** Decoding the hanging arm's SDMA queue against
`struct v10_sdma_mqd` from the kernel headers rather than reading the hex by eye
(`scripts/decode_sdma_mqd.py`):

| field | value | meaning |
|---|---|---|
| `rb_cntl` | 0x00061024 | ring control programmed |
| `rb_base` / `rb_base_hi` | 0x7f9b342000 | ring buffer allocated and its address written |
| `rb_rptr_addr_hi/lo` | 0x7f9c446ff010 | read-pointer writeback address programmed |
| `doorbell_offset` | 0x4800 | doorbell assigned |
| `rb_wptr` | 0x00000000 | **write pointer never advanced** |
| `rb_rptr` | 0x00000000 | read pointer at zero |
| `ib_size`, `status`, `context_status` | 0x00000000 | no indirect buffer, no status |

So the queue is fully set up and nothing was ever placed in its ring. That points
at the submission end rather than at the engine failing to consume or failing to
signal, which is the same conclusion as before but now resting on a decoded field
rather than on a mismatched comparison.

One caveat that keeps this short of proof: an MQD is a saved copy of queue state,
so a queue that was never mapped to hardware would show these same values. The
zero `context_status` is consistent with either. Distinguishing them needs a read
of the live doorbell or the hardware registers, which is the next step and is not
something this setup can currently do.
