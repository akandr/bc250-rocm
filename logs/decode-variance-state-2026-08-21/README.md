# What makes decode at depth vary between processes, 2026-08-21

Generated by `scripts/decode_variance_process_state.sh`.

Decode at a primed depth has varied run to run by as much as 15 percent on some
models throughout this work, with the clock pinned and temperature flat, and the
cause has been an open question since the first campaign. The one solid clue was
that repetitions inside a single invocation spread much less than separate
invocations of the same command, which places the variable in whatever differs
per process rather than in the decode loop.

First run: three arms, qwen3-8B Q8_0, decode of 8 tokens at a primed depth of
16128, six rounds with the arms rotated rather than blocked:

- A, default, as every decode measurement in this repository is taken
- B, pinned to CPUs 0 to 5, in case scheduling or migration matters
- C, page cache dropped and memory compacted before the run

| arm | n | mean t/s | sd | cv | range |
|---|---|---|---|---|---|
| A default | 6 | 17.67 | 1.35 | 7.7 percent | 16.23 to 19.79 |
| B pinned | 6 | 17.55 | 1.55 | 8.8 percent | 15.35 to 19.51 |
| C dropped and compacted | 6 | 17.23 | 0.50 | 2.9 percent | 16.52 to 17.77 |

## Reading

The means are indistinguishable. Whatever this is, it moves the spread and not
the throughput, which is consistent with everything else observed about it.

CPU pinning does nothing. Arm B is if anything slightly worse than the default,
so scheduling and migration can be set aside.

Starting from a dropped cache and compacted memory appeared to cut the spread to
about a third. Against arm A the variance ratio is 7.32 with 5 and 5 degrees of
freedom, two-tailed p 0.048; against arm B it is 9.53, p 0.027. Both cleared the
conventional threshold and neither cleared it comfortably. The confirmation
below shows this was a false positive.

## Confirmation: the effect is not real

It did not replicate, and the caution below was warranted rather than
decorative. Twelve rounds per arm, the two surviving arms only, ABBA
(`confirmation_log`, harness `scripts/decode_variance_confirm.sh`):

| run | arm A default | arm C dropped and compacted | variance ratio A/C |
|---|---|---|---|
| first, n=6 | sd 1.35, cv 7.7 percent | sd 0.50, cv 2.9 percent | 7.32 |
| confirmation, n=12 | sd 0.97, cv 5.4 percent | sd 0.90, cv 5.2 percent | 1.16 |
| pooled, n=18 | sd 1.08, cv 6.0 percent | sd 0.78, cv 4.5 percent | 1.93 |

The ratio collapses from 7.32 to 1.16. What moved is arm C: its spread went from
0.50 to 0.90, so the first result was that arm being unusually tight rather than
the treatment doing anything. Arm A's spread also fell, which is what regression
to the mean looks like when the first sample was small.

The mean difference does not survive either. Arm C reads about 0.5 t/s below arm
A in both runs, which was the one thing that looked consistent, but pooled over
18 runs per arm it is 17.87 against 17.35, Welch t 1.66 on 30.9 degrees of
freedom, two-tailed p 0.108.

So: dropping the page cache and compacting memory before a run changes neither
the spread nor the throughput of decode at depth. Together with the pinning arm,
that rules out both candidates this experiment was built to test.

## Why the caution was there

This board has form. Two careful designs of a graph-capture comparison here
returned differences of opposite sign, and the standing rule taken from that is
that any small effect needs a counterbalanced repeat before it means anything.
Both designs here were counterbalanced and the effect still evaporated, so the
rule needs strengthening rather than relaxing: on this board, a variance
difference at p just under 0.05 with six samples per arm is not evidence, it is
a starting point.

## One number that complicates the premise

The within-invocation comparison run alongside, eight repetitions in one process,
reported 19.87 plus or minus 1.02. That error bar is larger than arm C's spread
across six separate invocations, and more than twice the median of 0.43 recorded
for this measurement earlier. So the instrument's own error bar is itself
variable between invocations, and the clean statement that within-process spread
is about a third of between-process spread is less stable than it looked.
