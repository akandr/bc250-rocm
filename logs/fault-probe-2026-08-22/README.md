# Provoking the fault deliberately, 2026-08-22

Generated by `patches/faultprobe.hip`, `patches/faultbusy.hip` and
`scripts/fault_under_load.sh`.

## Why

`amdgpu.gpu_recovery=0` is proposed as the mitigation for the fatal reset, on the
strength of reading the driver: the fatal resets log `Source: 4`,
`AMDGPU_RESET_SRC_HWS`, and the function raising it is guarded by
`amdgpu_device_should_recover_gpu()`, which the parameter turns off. That is a
prediction. Waiting for a natural fault to test it means waiting days, since the
rate is roughly one per four boots. A fault can be caused on purpose instead: a
kernel writing far outside its allocation.

## The signature reproduces exactly

    Memory access fault by GPU node-1 on address 0x7f5557000000.
    Reason: Page not present or supervisor privilege.

    Faulty UTCL2 client ID: TCP (0x8)
    PERMISSION_FAULTS: 0x5
    RW: 0x1

Client, permission code and direction all match the faults that have killed this
board. So the fault itself is easy to cause.

## The escalation does not

Four variants, none of which produced a single reset or preemption failure:

| variant | what it did | resets | preemption or flush failures | board |
|---|---|---|---|---|
| idle, `gpu_recovery=0` | fault on an otherwise idle GPU | 0 | 0 | survived |
| idle, `gpu_recovery=-1` | the same at the driver default | 0 | 0 | survived |
| alongside load | fault fired while a separate `llama-bench` ran at depth | 0 | 0 | survived, benchmark completed at 85.23 t/s |
| own queues busy | 32 long kernels queued across 4 streams in the faulting process, then the bad write | 0 | 0 | survived |

A fifth attempt raised the footprint to 4 GiB per buffer and timed out at 300
seconds without reaching the fault, so it says nothing.

In every case the faulting process died with a memory access fault and the
driver reclaimed it without needing to reset anything.

## What that means

The mitigation is untested here. The parameter guards a path that none of these
probes takes, so running them proves nothing about it either way, and it would
have been easy to mistake "board survived with `gpu_recovery=0`" for a
confirmation. The control at the driver default survived identically, which is
what shows the parameter was never exercised.

It also narrows what the fatal chain needs. A page fault alone does not cause it,
not even one raised by a process holding many kernels in flight. Something about
the real events makes the subsequent queue preemption time out, and none of
these four reproduces it. The natural events all arose during long inference runs
that had been going for minutes to hours, so accumulated state rather than the
fault alone looks like the missing ingredient.

The fault hunt remains the only route to testing the mitigation, and it now runs
under the parameter.

Since this page was written the guard itself has been confirmed, by dropping the
requirement for a fault rather than by catching one: a module parameter that calls
`amdgpu_amdkfd_gpu_reset()` directly enters the same guarded path on demand
([`../kfd-reset-probe-2026-08-22/`](../kfd-reset-probe-2026-08-22/)). What remained
untested was the thing this page was trying to reach, a real fault under the
parameter, and whether the machine is still usable after one it declines to
reset. That was caught two days later: the host stays up, the GPU is unusable
until reboot and still enumerates normally, and every subsequent GPU process dies
([`../fault-usability-2026-08-24/`](../fault-usability-2026-08-24/)), which is one
fault observed once rather than a rate.
