# Inference logs from the July investigation


Generated by `scripts/decode_stats.sh` and `scripts/bench_prefill.sh`.

All from the 6.18-era stack, before the llama.cpp patches, the native rocBLAS
and the working boot configuration. They record what inference looked like when
it was mostly failing, and the top-level README cites them for that.

| file | what it shows |
|---|---|
| `bench_rocm_vs_vulkan.log` | the historical comparison: Vulkan running the small model at 1275 to 1845 t/s prefill on every run, ROCm managing about 35 t/s on pp128 and faulting on the rest |
| `rocm_prefill_works.log`, `rocm_decode_fails.log` | the split that shaped the early reading: prefill completing while decode faulted |
| `decode_aperture_violation.txt` | an `AMD_LOG_LEVEL=3` trace of the decode fault on one llama.cpp build |
| `decode_copybuffer_aperture_violation.txt`, `decode_copybuffer_aperture_violation2.txt` | the same fault on a later build, where it aborts on `__amd_rocclr_copyBuffer` with no compute kernel dispatched first, which moved the reading from a decode-kernel bug to a memory-mapping one |
| `decode_campaign_stats.txt` | a single-boot campaign classifying each decode attempt, showing the intermittent model load as the dominant blocker rather than the decode itself |

Two of the conclusions drawn from these have since been retracted in the
top-level README. The load-time failures were the allocation-reuse defect and
are fixed by the runlist flush. The "loads hang on every boot" reading in the
same period was a harness mistake, a newer llama.cpp CLI ignoring `-no-cnv` and
spinning on a closed stdin; the loads had in fact completed.
