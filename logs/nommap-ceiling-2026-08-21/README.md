# Loading without mmap lowers the usable context, 2026-08-21

Generated by `scripts/nommap_ceiling.sh`.

Found by accident, which is worth saying: a decode-variance experiment used
`--load-mode none` as one arm and every run of that arm failed while the mmap
arm succeeded, eight times out of eight. The experiment measured nothing and the
failure was the result.

## What happens

qwen3-8B Q8_0, decode of 8 tokens with the cache primed, everything else held
fixed:

| load mode | primed depth | outcome |
|---|---|---|
| none | no depth | 35.62 t/s |
| none | 8192 | 25.26 t/s |
| none | 12288 | 21.23 t/s |
| none | 14336 | 21.33 t/s |
| none | 16128 | aborts, 10 of 10 attempts |
| mmap | 16128 | 15.51 and 17.87 t/s (see below) |

The abort is a `ROCm error` raised from `ggml_cuda_graph_evaluate_and_capture`
at `ggml-cuda.cu:109`. Its detail line is lost: `GGML_LOG_ERROR` writes to
stderr and the buffer does not survive the `GGML_ABORT` that follows, so the
shipped logs carry the location but not the message.

## Why

Memory, and it is measured rather than inferred. Sampling `free` every two
seconds through both arms at depth 16128:

| arm | peak used | minimum available |
|---|---|---|
| load mode none | 14594 MiB | 601 MiB |
| load mode mmap | 11532 MiB | 3663 MiB |

Without mmap the 8.24 GiB of weights are anonymous memory and cannot be
reclaimed. With mmap they are page-cache backed, so the kernel can evict them
under pressure and the same workload peaks about 3 GiB lower. On a board where
14 GiB is shared between host and GPU, that difference is the whole margin.

## Why it was never seen before

Every previous decode-at-depth measurement in this repository used
`llama-bench` without a load-mode flag, and the default is mmap. The perplexity
gates do pass `--no-mmap`, but at context 4096, far below where this bites. So
the configuration that fails is one this work had not run, rather than a
regression in one it had.

## Note on the flag

`-mmp` is deprecated in this build in favour of `--load-mode`. Both spellings
were tried and both fail identically at depth 16128, so this is the semantics of
loading without mmap and not an artifact of the deprecated flag.

Corrected on 25 August. The mmap row previously listed six values, 15.51, 16.92,
16.05, 18.60, 18.59 and 17.87. Only the first and last are captured, in
`lm_mmap_d16128.log` and `rerun_mmap.log`; the middle four appear nowhere in this
repository, not in this directory and not in any other decode-at-depth log. Every
`tg8 @ d16128` reading anywhere in `logs/` was listed and checked against them.
They were presumably read from a terminal and not kept.

Nothing on this page depends on them. The claim is that the mmap arm completes at
a depth where the no-mmap arm aborts ten times out of ten, and two completed runs
establish that as well as six would. The decode rate itself is not the point here
and is characterised properly elsewhere, in
[`../loose-ends-2026-08-18/variance/`](../loose-ends-2026-08-18/variance/), where
ten runs at this depth span 16.21 to 18.71.
