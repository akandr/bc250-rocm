# A GPU reset kills this board, with or without a fault, 2026-08-21

Generated by `scripts/gpu_reset_test.sh`.

## Why this was tried

Every fatal event on record ends the same way: `GPU reset begin!`, then a couple
of seconds, then the board is gone. Three of the five have no line saying the
reset finished. That is consistent with two quite different readings. Either the
reset is fatal on this hardware, or the state it was called from, after a page
fault and a failed queue preemption, was already unrecoverable and the reset
never had a chance.

Those are separable, because a reset can be requested deliberately. Reading
`/sys/kernel/debug/dri/0/amdgpu_gpu_recover` asks the driver to recover the
device. Doing that with the GPU idle removes the fault, the workload, the
preemption timeout and the failed runlist rebuild, leaving only the reset.

## Result

The board dies. Twice out of two attempts, from a completely idle GPU with no
HIP process running:

| attempt | before | after |
|---|---|---|
| 1 | uptime 78758s, governor active, GPU idle | unreachable, rebooted itself, back after about two minutes |
| 2 | uptime 63s, governor active, GPU idle | unreachable, did not come back, needed a power cycle |

Nothing survives in the journal. The probe logs its own line before triggering
and that line is there; after it, the persistent journal for that boot contains
no further kernel output at all, not even `GPU reset begin!`. The board goes
away faster than the log can be flushed.

That is more abrupt than the fault-induced resets, which do manage to log the
reset beginning and several lines after it.

## What this changes

The reset, not the fault, is the step that kills the board. The page fault,
the preemption timeout and the runlist rebuild returning -62 are how a reset
comes to be requested, but any reset appears to end the same way. So the defect
splits in two, and the second half is the one that matters for usability:

- something causes a GPU fault under load, rarely, still unidentified
- a GPU reset on this board is not survivable, which turns any such fault into
  a dead machine rather than a dead process

## Caveats

Two attempts is thin for a claim this size, and both used the debugfs path
rather than the driver's own internally triggered recovery. Those converge on
`amdgpu_device_gpu_recover` but are not identical entries.

It is also possible this is ordinary for an APU rather than a defect of this
board. The GPU here is part of the SoC and shares memory with the host, so a
device reset is a far more invasive operation than it is on a discrete card,
and it may simply not be a supported thing to do. Nothing here distinguishes
"this board is broken" from "resetting an integrated GPU takes the system with
it". A second BC-250, or any other Cyan Skillfish system, would settle it.

## What follows from it

If resets are fatal and faults are rare, the practical question is whether the
driver can be told not to attempt one. `amdgpu.gpu_recovery=0` disables recovery,
which should leave a faulting process dead and the GPU wedged but the host
alive, which is a much better failure than a reboot.

The board now boots with that parameter and the fault hunt runs under it. Two
things are established already. It is in effect, `/sys/module/amdgpu/parameters/
gpu_recovery` reads 0, and it costs nothing measurable: three runs give 783.80,
784.08 and 797.56 prefill with 112.73, 112.76 and 110.66 decode, against 805.53
and 113.50 recorded before the parameter existed, which is inside the spread this
measurement has always shown
([`../gpu-recovery-cost-2026-08-21/`](../gpu-recovery-cost-2026-08-21/)).

Getting that second number right took a correction. The first measurements under
the new parameter read 84.81 prefill and 32.19 decode, then 181.94, 151.60 and
141.45 across three more runs, which looked like the parameter wrecking
performance and degrading further each run. It was not. The fault hunt is a
systemd service with `Restart=always`, so it had started automatically on the
reboot and was running an 8B benchmark continuously underneath the measurements.
Pausing it gave the normal figures immediately. A benchmark that has to share the
GPU measures the sharing.

Triggering the debugfs knob again under `gpu_recovery=0` still killed the board,
which looks at first like the parameter being useless. It is not, and the driver
source says why. The debugfs handler, `gpu_recover_get` in `amdgpu_fence.c`,
schedules `adev->reset_work` directly, and `amdgpu_debugfs_reset_work` builds a
context with `AMDGPU_RESET_SRC_USER` and `AMDGPU_NEED_FULL_RESET` and calls
`amdgpu_device_gpu_recover` without ever consulting
`amdgpu_device_should_recover_gpu()`, which is the only place the parameter is
read. So that path forces a reset whatever the parameter says, and the arm is
uninformative about the question it appeared to answer.

The fault path is different, and this is the useful part. Every fatal reset on
record logs `Source: 4`, which is `AMDGPU_RESET_SRC_HWS` in the enum in
`amdgpu_reset.h`, the hardware scheduler. That source is set in
`amdgpu_amdkfd.c`, and the function that raises it reads in full:

    void amdgpu_amdkfd_gpu_reset(struct amdgpu_device *adev)
    {
            if (amdgpu_device_should_recover_gpu(adev))
                    (void)amdgpu_reset_domain_schedule(adev->reset_domain,
                                                       &adev->kfd.reset_work);
    }

`amdgpu_device_should_recover_gpu()` returns false immediately when
`amdgpu_gpu_recovery == 0`. So under this parameter the reset that has been
killing the board is not merely survived, it is never requested.

That is a prediction from reading the source, not a measurement. What it
predicts is that the next fault leaves a dead process and a wedged GPU on a live
host. The fault hunt runs under the parameter and will show whether that is what
happens. Until a fault occurs there is nothing empirical to report.
