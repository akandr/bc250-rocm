# Inside the KIQ resume, and the stall moves when you add prints, 2026-08-23

Generated by `scripts/kiq_init_bisect.sh`, installed with
`scripts/install_probe_module.sh`, triggered through debugfs and captured over
netconsole after verifying the listener with a `/dev/kmsg` marker each time.
Prediction in `prediction.txt`, captures in `run1_coarse.log` and `run2_fine.log`.

## Two runs, two stop points

`gfx_v10_0_kiq_resume()` is a one-line wrapper around
`gfx_v10_0_kiq_init_queue()`, whose reset path is seven steps. Instrumenting
those steps:

**Run 1**, prints at the seven step boundaries:

    BC250KIQ 1 before kiq_setting
    (nothing further)

**Run 2**, the same prints plus three more splitting the register read and write
inside `kiq_setting`:

    BC250KIQ 1 before kiq_setting
    BC250KIQ 1a before RREG32 mmRLC_CP_SCHEDULERS
    BC250KIQ 1b read returned 0x5850c0c8
    BC250KIQ 1c write complete
    BC250KIQ 2 after kiq_setting, in_reset=1
    BC250KIQ 3 before memcpy_toio backup=0000000008cb8b9b
    BC250KIQ 4 after memcpy_toio
    BC250KIQ 5 after clear_ring
    BC250KIQ 6 got srbm_mutex
    BC250KIQ 7 after grbm_select
    (nothing further, so gfx_v10_0_kiq_init_register never returns)

The same code, the same trigger, and the failure point moved. In run 2 the
register read that run 1 apparently died on returns a value, 0x5850c0c8, and the
write completes.

## What that means

The stall is not attached to one instruction. Adding prints adds delay, each one
a `dev_warn` that netconsole then ships over UDP, and with that extra delay the
sequence gets six steps further before stopping. That is the signature of a
device that needs time to settle after a reset rather than of a single broken
access.

So the honest statement is: the KIQ initialisation sequence stalls somewhere
inside it, the exact point depends on timing, and slowing the sequence down moves
the failure later. Run 2's last unreturned call, `gfx_v10_0_kiq_init_register()`,
is where it stopped that time, not where it always stops.

## The prediction, judged

It named steps 2 or 6, the `memcpy_toio` or `kiq_init_register`, on the reasoning
that an MMIO access to a device whose memory has just been torn down would not
complete. Run 2 stops at step 6, which is one of the two named. Run 1 stopped at
step 1, which is neither.

Given the two runs disagree, the prediction cannot be called confirmed. The
reasoning behind it, that this is an MMIO access that does not complete, is still
consistent with everything seen, including the host-side clocksource watchdog
that ends every capture. But a prediction that matches one run of two is not
evidence, and it is recorded as unresolved rather than as a hit.

## What this opens

If the device needs time to settle, a delay before the KIQ initialisation may
avoid the stall entirely. That is a testable fix rather than another
localisation, and it is the obvious next step.

## What happened next, added 25 August

Both halves of this page were overtaken and neither survives as written. The
settle hypothesis was tested directly and refused: an explicit `msleep()` of
50 ms and then 500 ms before the KIQ initialisation changes nothing, and the
stall happens as before
([`../reset-settle-delay-2026-08-24/`](../reset-settle-delay-2026-08-24/)). So the
delay each print costs is not what moved the failure point.
What did was repetition. Every configuration on this page was run once, and
running them repeatedly shows the stopping point varies between identical runs,
so these two captures are two samples of a race rather than two placements
([`../reset-kiq-repeat-2026-08-24/`](../reset-kiq-repeat-2026-08-24/)). The
current statement is that the first GC register access after a reset hangs,
whichever one it happens to be
([`../reset-path-2026-08-24/`](../reset-path-2026-08-24/)). This page is kept
because the reasoning it rejects, that the stall is attached to one instruction,
is rejected correctly and for a reason that still holds.
