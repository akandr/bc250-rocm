# The fault hunt, and what it did not find, 2026-08-22

Generated by `scripts/fault_hunt.sh`, run as a systemd unit so it survived the
board rebooting under it.

## What it was for

`amdgpu.gpu_recovery=0` is the proposed mitigation for the fatal GPU reset, and
it is traced through the driver source rather than measured. Confirming it needs
a natural fault, because four deliberate ones reproduce the signature without
triggering the escalation the parameter guards. The hunt ran the fault-prone
workload continuously to catch one, and from 22 August also ran a correctness
gate every fifth round so the same hours produced endurance evidence.

## Result

| quantity | value |
|---|---|
| iterations | 255 |
| boots covered | 16 |
| correctness gates run | 15 |
| distinct gate values | 1, `8.9442` on every one |
| natural faults caught | 0 |

The single archive under `hits/` that is not marked deliberate is the soak crash
of 20 August, which the hunt archived from the previous boot when it first
started. It found nothing new.

`natural_boot0.txt` is that archive, kept because it is the only complete record
of a natural event: a gfxhub page fault on vmid 8, `PERMISSION_FAULTS: 0x5`, a
write, followed by `GPU reset begin!. Source: 4`.

## What the absence means

Less than it might. The earlier figure of five fatal resets across twenty
retained boots came from days of varied work: long soaks, model loads at several
sizes, PyTorch, allocation churn, deliberate A/B batteries. The hunt ran one
workload repeatedly, decode at a primed depth of 16128 on the 8B. Two hundred
and fifty-five iterations of that produced no fault, which suggests the rate is
not uniform across workloads, and that whatever accumulates before a fault is
not something this particular loop accumulates.

It is consistent with the finding from the deliberate probes, that a page fault
needs more than a busy GPU to escalate. Both point at the ingredient being
something about long, varied sessions rather than sustained load alone.

## Status of the mitigation

Untested when this was written, and both halves of that were settled within two
days, added 26 August. The escalation was reproduced deliberately the same
evening, by calling the guarded path through a module parameter rather than
waiting for a fault to reach it, which killed the board at the driver default and
returned harmlessly with `gpu_recovery=0`
([`../kfd-reset-probe-2026-08-22/`](../kfd-reset-probe-2026-08-22/)). And a
natural fault was caught on 24 August by a second hunt that ran the fault-prone
workload rather than this one, after about 190 rounds: the host survived, the GPU
never recovered, and every later GPU process died
([`../fault-usability-2026-08-24/`](../fault-usability-2026-08-24/)). The defect
entry no longer says untested.
