# The reset hangs in the KIQ resume, 2026-08-23

Generated by `scripts/cp_resume_bisect.sh`, installed with
`scripts/install_probe_module.sh`, triggered through debugfs and captured over
netconsole after verifying the listener with a `/dev/kmsg` marker. The prediction
was written before the run and is in `prediction.txt`.

## Result

    GPU reset begin!. Source:  5
    SMU is resuming...
    SMU is resumed successfully!
    BC250CP before kiq_resume
    clocksource: Watchdog remote CPU 10 read timed out

`gfx_v10_0_kiq_resume()` is entered and never returns. No `kiq_resume returned`
line, no `before kcq_resume`, nothing further.

So the host stall after a GPU reset is the Kernel Interface Queue failing to
resume.

## The prediction

It was registered in advance, and it was right for the stated reason. The
sequence inside `cp_resume` is microcode load, then KIQ resume, then KCQ resume,
then the graphics ring path. The prediction named steps two or three, KIQ or KCQ,
on the grounds that this board's weakness has always been on the compute side:
its correctness defect was a PASID flush issued through the KIQ, fixed by
`bc250_flush_pasid_kiq=0`; its compute queues are the ones Mesa disables on
gfx1013; its preemption timeouts are on compute queues.

It is the KIQ, the first of the two.

## What this ties together, and how firmly

This is the same queue as the original defect. `bc250_flush_pasid_kiq=0` exists
because a PASID flush issued through the KIQ froze this board; the fix is to stop
using the KIQ for that flush. Now a GPU reset is found to hang because the KIQ
cannot be brought back.

Two defects, one queue. That is a much tighter connection than "both are in the
CP", which was as far as the previous cycle could go. It is still not proof of a
single root cause: a queue that misbehaves when flushed through and a queue that
cannot be re-initialised after a reset could be two faults in one block. But any
account of this hardware now has to explain the KIQ.

## Scope

One board, one kernel, one reset method reaching this path. The KIQ resume was
reached identically in every capture of this defect, but only this run
instrumented it.

## One capture

One triggered reset. This page carries the load-bearing step of the whole reset
chain, that `gfx_v10_0_kiq_resume()` is entered and never returns, and it rests
on a single netconsole capture where that was the last line to arrive. Netconsole
is UDP with no retransmission, so an absent line can mean a stall or a lost
packet. The repetition that tests this is in
