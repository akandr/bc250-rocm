# Rebinding amdgpu as a recovery path, 2026-09-15

Generated by [`scripts/rebind_recovery_test.sh`](../../scripts/rebind_recovery_test.sh), kernel 7.1.8,
experiment module with production settings, `gpu_recovery=0`, one fresh boot per trial, netconsole.

A GPU wedged by a fault stays unusable until reboot
([`../fault-usability-2026-08-24/`](../fault-usability-2026-08-24/)), and neither a reset (none exists
for this chip) nor a gfx9-style queue reset recovers it
([`../reset-honest-2026-09-15/`](../reset-honest-2026-09-15/)). Unloading and reloading the driver
was the untested candidate. The wedge trigger is the PASID-filtered rebuild under a `--no-mmap`
load ([`../tlb-alt-2026-09-15/`](../tlb-alt-2026-09-15/), round 4).

| trial | GPU before | unbind | bind | outcome |
|---|---|---|---|---|
| R0 | healthy (tg16 114.51) | rc 0, 0 s | host stops answering | power cycle |
| R1 | wedged (4 preemption failures, smoke fails) | rc 0, 4 s | host stops answering | power cycle |
| R2 | wedged (same) | rc 0, 4 s | host stops answering | power cycle |

Every bind ends the same way, in `R*.netconsole.log`: the driver runs the 40-CU unlock, which reads
`SPI=0x0000001f` (the value the previous probe wrote, so the hardware was not reset in between),
and within two seconds `clocksource: Watchdog remote CPU n read timed out`. That is the signature of
the reset defect in [`../reset-kiq-repeat-2026-08-24/`](../reset-kiq-repeat-2026-08-24/): initialising
a GC block that was never reset hangs the first register access.

So a driver reload is not a recovery path on this chip. It is the same operation as the no-op reset,
re-initialising live hardware, reached from a different direction, and it fails even on a healthy GPU.
Unbinding alone is harmless.
