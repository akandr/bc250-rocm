# The SVM map-side flush: ftrace evidence and A/B batteries, 2026-08


Generated by `scripts/aba_mapflush_verify.sh`.

Evidence behind the claim that the allocation-reuse fault is a stale
translation surviving into a fresh mapping, and that rebuilding the runlist on
the KFD SVM *map* path is what closes it.

| file | what it is |
|---|---|
| `inv28.log` | the ftrace run that located the fault in time: it lands 44 to 122 microseconds after a remap of the faulting range |
| `dmesg_r1.txt`, `dmesg_r2.txt` | the kernel side of those two runs |
| `func_counts.txt` | function-profile counts during a faulting run, showing the traffic going through `svm_range_validate_and_map` and `svm_range_unmap_from_gpus` rather than the ioctl path the original hook covered |
| `aba-verify.log` | A/B/A on one boot with the parameter toggled live |
| `aba-verify-freshboot.log`, `aba-verify-freshboot-summary.txt` | the same across a reboot, with the value set from the kernel command line |
| `aba-verify-mapioctl-ineffective.log` | the control that ruled out the map-side *ioctl* hook, which is not where the fix belongs |
| `torch_aba.log` | the same A/B against PyTorch's varying-size allocation churn |

The headline tally across everything run this way is 84 churn sweeps with the
map side enabled, all completing with no faults, against 12 with it disabled, of
which 2 completed and 10 faulted. The disabled arm is therefore not
deterministic, which is why the top-level README says it fails most of the time
rather than always.
