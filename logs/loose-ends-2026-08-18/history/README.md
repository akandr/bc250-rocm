# Does prior heavy work explain the 8B decode outlier? 2026-08-18

Generated by `scripts/decode_history_control.sh`.

The companion measurement in `../variance/` found the 8B decode rate varies by
15 percent within one boot, with a coefficient of variation of 4.3 percent, and
that one earlier reading of 12.94 sat 6.3 standard deviations below that mean.
The obvious explanation was memory state: this is a 16 GiB shared board, the
model is 8.24 GiB, and the low reading came from a session that had been
running large models for hours.

## Result: it does not

Same workload, same boot, three conditions:

| condition | runs |
|---|---|
| clean board, nothing large run yet | 18.00, 18.51 |
| immediately after a 10.7 GiB MoE loaded and ran | 17.88, 18.78 |
| after dropping caches and compacting memory | 19.23, 18.26 |

All six overlap, and the 8 percent spread across them is what the intrinsic
4.3 percent coefficient of variation predicts. Prior heavy work does not
depress the rate.

One observation that undermined the hypothesis before the numbers did: free
memory was about 14.5 GiB at the start of every condition, including
immediately after the MoE run. The MoE process had exited and its memory was
returned, so there was no lasting pressure for the next run to inherit.

## What remains of the outlier

The 12.94 reading is the only 8B decode figure in this work that was taken
interactively and never written to a log, so unlike the other twelve it cannot
be re-examined. It was measured minutes before a run at a larger context that
aborted with `SVM mapping failed, exceeds resident system memory limit`, so the
board may already have been in the state that run then hit. That is a
suggestion rather than a finding, and the honest summary is that the range from
captured evidence is 16.21 to 18.71 and the outlier is unexplained.
