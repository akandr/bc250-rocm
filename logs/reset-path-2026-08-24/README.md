# It is not one register: the first GC access after a reset is what hangs, 2026-08-24

Generated by [`scripts/kiq_reg_probe.sh`](../../scripts/kiq_reg_probe.sh) for the
module and [`scripts/reset_trial_repeat.sh`](../../scripts/reset_trial_repeat.sh)
for the trials, installed with
[`scripts/install_probe_module.sh`](../../scripts/install_probe_module.sh),
triggered by reading `amdgpu_gpu_recover` under the device's debugfs directory and
captured over netconsole after verifying the listener with a `/dev/kmsg` marker
before every trigger. Predictions in `predictions.txt`, written before any trial;
`notes.txt` records a capture that was lost and what was done about it.

## What was asked

The stall after a GPU reset is an MMIO read to the GC block that does not return,
and it is intermittent ([`../reset-kiq-repeat-2026-08-24/`](../reset-kiq-repeat-2026-08-24/)).
What that did not say is how much of the block is unreachable. The bisect had
arrived at `mmRLC_CP_SCHEDULERS` because that is the register
`gfx_v10_0_kiq_setting()` happens to touch, which is not the same as that register
being special. This probe reads PCI config space, then `mmGRBM_STATUS`, then
`mmSCRATCH_REG0`, then `mmRLC_STAT`, and only then the scheduler register,
printing each value as it returns and numbering every line so a lost packet can be
told from a stall.

## Result, five triggered resets

Every trial ends the same way:

    BC250REG 1 pci config dword0 = 0x13fe1002
    BC250REG 2 pci command/status = 0x00100407
    BC250REG 3 rmmio_size=524288 sched_off=0xecaa grbm_off=0x2004
    BC250REG 4 about to read GRBM_STATUS
    clocksource: Watchdog remote CPU N read timed out

Line 5 never arrives in any of the five. The numbering is contiguous up to 4 every
time, so this is a stall and not packet loss.

## What that changes

**The RLC is not implicated, and neither is any particular register.** The read
that hangs is simply the first GC register access after the reset. In the driver's
own path that was `mmRLC_CP_SCHEDULERS`; give the probe an earlier access and the
stall moves to that instead. Every localisation below the GFX resume should be read
as "the first access this build happens to make" rather than as naming a register.

**The device is present and the link is up.** Config space reads return
`0x13fe1002`, the AMD vendor id with this part's device id, and a command word of
`0x0407` with memory space and bus mastering enabled. Whatever fails, it is not the
device having fallen off the bus, which would also have made the reset's own
success messages impossible.

**It is not the indirect register path.** `rmmio_size` is 524288 bytes and the two
offsets are dword indices, so the scheduler register sits at byte 0x3B2A8 and
`GRBM_STATUS` at 0x8010, both inside the mapped window. amdgpu therefore takes the
direct path, a plain `readl` on the BAR, rather than the PCIE index/data pair that
serialises on `adev->pcie_idx_lock`. A spinlock held by another stuck CPU had been
a live explanation for a CPU that stops answering, and it is not this.

So what is left is narrow: after a MODE1 reset on this part, a plain load to the
mapped GC aperture intermittently never completes, while config space stays
responsive. The CPU that issued it stops answering, which is what the clocksource
watchdog is reporting.

## One observation that has no artifact

The first trial run of this probe, before the harness was fixed, showed
`GRBM_STATUS` returning `0x00003028` with the following read of `mmSCRATCH_REG0`
hanging. Rerunning the harness restarted its trial numbering and overwrote that
capture before it was committed. Five subsequent trials did not reproduce it.

It is recorded here as an observation without evidence, not as a finding. It is
consistent with the intermittency measured elsewhere, roughly one run in twelve
getting an access through, and one unreproduced run out of six is what that rate
predicts. But nothing here rests on it, and if the aperture's reachability turns
out to matter, it needs collecting again rather than citing.

## The other path, and an assumption retired

Everything above was triggered through debugfs, which enters by
`amdgpu_device_gpu_recover()` with `AMDGPU_RESET_SRC_USER` and logs `Source: 5`.
The resets that take this board down under load enter by
`amdgpu_amdkfd_gpu_reset()` with `AMDGPU_RESET_SRC_HWS` and log `Source: 4`. That
the two fail the same way had been assumed since the bisect began, and the whole
localisation depends on it: if they diverge, all of this describes a reset nobody
cares about.

The same module carries a parameter that calls the KFD path directly, so the arm
only needed a boot with `amdgpu.gpu_recovery` at the driver default, since the
guard is what that parameter turns off. `cmdline_before.txt` records the command
line that was restored afterwards.

| trial | reset source | last line to arrive |
|-------|--------------|---------------------|
| path-debugfs_rep1 | `Source: 5` | `BC250REG 4 about to read GRBM_STATUS` |
| path-debugfs_rep2 | `Source: 5` | `BC250REG 4 about to read GRBM_STATUS` |
| path-debugfs_rep3 | `Source: 5` | `BC250REG 4 about to read GRBM_STATUS` |
| path-debugfs_rep4 | `Source: 5` | `BC250REG 4 about to read GRBM_STATUS` |
| path-debugfs_rep5 | `Source: 5` | `BC250REG 4 about to read GRBM_STATUS` |
| path-kfd_rep1 | `Source: 4` | `BC250REG 4 about to read GRBM_STATUS` |
| path-kfd_rep2 | `Source: 4` | `BC250REG 4 about to read GRBM_STATUS` |
| path-kfd_rep3 | `Source: 4` | `BC250REG 4 about to read GRBM_STATUS` |

The KFD arm's own words, with the guard reporting that it will proceed:

    BC250KFDRESET: calling amdgpu_amdkfd_gpu_reset, gpu_recovery=-1, should_recover=1
    BC250KFDRESET: returned
    GPU reset begin!. Source:  4
    MODE1 reset
    BC250REG 1 pci config dword0 = 0x13fe1002
    ...
    BC250REG 4 about to read GRBM_STATUS
    clocksource: Watchdog remote CPU 8 read timed out

Two entry points, two reset sources, eight trials, one failure. The localisation
collected through debugfs describes the reset that actually takes this board down,
and that is an observation now rather than an assumption.

What it does not make observable is the fault that requests the reset in the
first place. These are still deliberate resets on an idle GPU; what a real fault
adds is a wedged queue underneath, and nothing here says whether that changes the
outcome.
