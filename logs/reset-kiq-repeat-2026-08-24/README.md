# The reset stall is a race, and three earlier readings were single runs of it, 2026-08-24

Generated by `scripts/kiq_read_probe.sh` for the module and a runner since
generalised into [`scripts/reset_trial_repeat.sh`](../../scripts/reset_trial_repeat.sh),
installed with [`scripts/install_probe_module.sh`](../../scripts/install_probe_module.sh),
triggered by reading `amdgpu_gpu_recover` under the device's debugfs directory and
captured over netconsole after verifying the listener with a `/dev/kmsg` marker
before every trigger. Predictions in `predictions.txt`, written before any trial
ran; `notes.txt` holds two observations made during the campaign and kept apart
from the pre-registration. One capture per trial, `A_rep1.log` through
`D_rep3.log`, rendered by
[`scripts/kiq_repeat_summary.sh`](../../scripts/kiq_repeat_summary.sh).

## Why repetition rather than another placement

A GPU reset succeeds on this board and the host then stalls. Bisecting the resume
had reached a single MMIO read, `RREG32_SOC15(GC, 0, mmRLC_CP_SCHEDULERS)` in
`gfx_v10_0_kiq_setting()`. Three readings had been built on top of that in two
days, and each came from one run: that the device needed settling time, that
intervening bus activity between two register accesses helped, and that where the
prints sat was what moved the stopping point. The first was falsified by an
`msleep` that changed nothing at 50 or 500 milliseconds. The second was falsified
by a probe that printed nothing at all, because it sat downstream of the read it
was meant to measure.

What had never been done was running the same thing twice. This campaign is four
configurations, three repetitions each, against one module, with only runtime
parameters differing between arms:

| arm | before the read | between read and write |
|-----|-----------------|------------------------|
| A | nothing | nothing |
| B | a print | a print |
| C | `msleep(50)` | nothing |
| D | a print | nothing |

Eleven of twelve stall with the read never returning. One does not. D rep2 is the
same module, the same parameters and the same trigger as D rep1 and D rep3, and
it went further:

    BC250ACT before read
    BC250ACT step 1 kiq_setting returned
    BC250ACT step 2 mqd restored
    BC250ACT step 3 ring cleared
    BC250ACT step 4 grbm selected
    clocksource: Watchdog remote CPU 7 read timed out

The read returned, four steps ran, and the stall moved to
`gfx_v10_0_kiq_init_register()`.

## What that settles

The claim under test was that the build determines where the sequence stops. One
counterexample is enough, and D rep2 is it. `predictions.txt` registered the
consequence before the data: the stopping point is not determined by the build,
every placement conclusion drawn so far is unsupported, and the right description
of this defect is a race rather than a bad access.

It also explains the run of 23 August without appealing to prints at all. That run
reached step 7 and stalled in `gfx_v10_0_kiq_init_register()`, which is where
D rep2 stalled with no extra prints anywhere. The build was not what let it get
further. It was a run that happened to get further, and it became a mechanism
because it was the only run of that build.

So the description that survives is: after a reset, MMIO accesses to the GC block
intermittently do not complete, and where the sequence stops varies between
identical runs. On this sample the read completes about one time in twelve, which
is a first rate on a small sample and not a measured one.

## What it does not settle

Nothing here says why an MMIO read to that block does not return. It does not
distinguish one register from the whole block, which
[`scripts/kiq_reg_probe.sh`](../../scripts/kiq_reg_probe.sh) is built to ask by
reading a global, a scratch and an RLC register before the one that hangs.

And it inherits an assumption the whole bisect rests on. Every trial here was
triggered through debugfs, which enters by `amdgpu_device_gpu_recover()` with
`AMDGPU_RESET_SRC_USER`. The resets that take this board down under load enter by
`amdgpu_amdkfd_gpu_reset()` with `AMDGPU_RESET_SRC_HWS`. That the two fail the
same way has never been observed; the sequence for checking it is in
[`scripts/reset_path_compare.sh`](../../scripts/reset_path_compare.sh).

## A note on the instrument

Netconsole is UDP with no retransmission, so a dropped packet and a stall produce
the same evidence. C rep1 is the demonstration: its capture ends on the 40-CU
unlock, without the watchdog line every other trial carries, although the reset
fired and ran the same way. Every localisation in this investigation has the form
"this line printed and nothing after it did", which assumes delivery. Repetition
is what separates the two, and the next probe numbers its lines so that a gap
reads as a gap.
