# The zeroed fp16 GEMM is one per batch boundary, and a single batch avoids it, 2026-08-23

Generated by `scripts/ubatch_zero_test.sh`.

## The prediction

The zeros land on the first fp16 GEMM of every evaluated batch after the first.
If that is the mechanism rather than a coincidence, then changing the micro-batch
size changes the number of zeros exactly, because it changes the number of
batches. Predictions were written into the harness header before running:

    ub 2048 -> one batch    -> 0 zeros
    ub 1024 -> two batches  -> 1 zero
    ub 512  -> four batches -> 3 zeros
    ub 256  -> eight batches -> 7 zeros

## Result

| ubatch | batches | GEMM calls | zeros | at | perplexity |
|---|---|---|---|---|---|
| 2048 | 1 | 36 | 0 | | 7.2768 |
| 1024 | 2 | 72 | 1 | 37 | 11.7443 |
| 512 | 4 | 144 | 3 | 37, 73, 109 | 14.1344 |
| 256 | 8 | 288 | 8 | 37, 73, 109, 145, 181, 217, 253, 254 | 20.0773 |

Three of the four are exact. The calls per batch stay at 36 regardless of batch
size, which makes sense since that count follows the model's layers rather than
the token count, so the zeros sit 36 apart throughout.

The eight-batch case has one more zero than predicted, at call 254, immediately
after the expected one at 253. Seven of the eight fall exactly where the model
says. The extra adjacent zero is unexplained.

The damage tracks the zero count monotonically: one batch 7.2768, two 11.7443,
four 14.1344, eight 20.0773.

## A single batch is correct, and deterministic

| configuration | perplexity |
|---|---|
| f32 compute, ub 2048 | 7.2672 |
| f32 compute, ub 512 | 7.2672 |
| fp16 compute, ub 2048 | 7.2768, 7.2768, 7.2768 |
| fp16 compute, ub 512 | 14.6752 |

With one batch the fp16 path sits 0.13 percent from the f32 reference, which is
ordinary half-precision rounding, and it repeats to four decimals three times.
The non-determinism that has characterised this defect throughout is absent. The
f32 arm is unaffected by batch size, as expected, since it does not take the
path.

## What this gives

A second workaround, and one that does not require forcing the compute type:
evaluating in a single batch avoids the defect entirely. That is only practical
where the context fits in one micro-batch, so it does not replace
`GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` as the general recommendation, but it is a
sharp diagnostic.

More importantly it moves the defect from "something about fp16 GEMMs" to
"something that happens at a batch boundary and damages the first fp16 GEMM
after it". Whatever is reused, rebound or reallocated between batches is now the
place to look, and the first batch of a process being clean says the state has to
be established by a batch before it can go wrong.
