# What `HSA_OVERRIDE_GFX_VERSION` does to a kernel you built yourself, 2026-08-26

Generated by [`scripts/override_trap_probe.sh`](../../scripts/override_trap_probe.sh), both arms
the same binary on the same boot, back to back, kernel 7.1.8. `probe.out` is the run and
`state.txt` records the boot line.

This exists because `INVESTIGATION.md` carried the result as a two-row table with nothing behind
it. The table is a safety warning about a workaround people are still told to use, and no probe log
in this repository held either of its timings. A figure audit widened to one decimal place reached
it on 26 August.

| configuration | result | kernel time |
|---|---|---|
| no override | `wrong=0/4194304`, ALL CORRECT | 1933.0 ms |
| `HSA_OVERRIDE_GFX_VERSION=10.1.0` | `wrong=4194304/4194304`, first mismatch at index 0 `got 0, want -2109779631` | 0.1 ms |

The claim holds, and the mechanism is visible in the probe's own banner: without the override it
reports `compute_probe gfx1013:xnack-`, with it `gfx1010:xnack-`. The gfx1013 code object no longer
matches the device the runtime now claims to have, the launch does nothing, the output buffer keeps
the zeros it was allocated with, and the process exits `rc=3` only because the probe checks its own
answers against the CPU. Nothing in `dmesg` records it: the fault count for the whole run is zero.

The timing the table quoted, 1994.9 ms, is not what this run measured. 1933.0 ms is 3 percent
faster and sits inside the 1880 to 1978 ms band the other probe captures in this repository show at
this size, so the quoted value was plausible but was not a reading anyone kept. The 0.1 ms under
the override reproduces exactly, which is the number the argument actually rests on: a dispatch
that returns in a tenth of a millisecond where the real thing takes about two seconds did not run.

One note on the instrument, added the same day. The run captured here counted faults with `dmesg`
alone, and the shared audit flagged that: `dmesg` cannot see a fault from a boot that ended in a
reset, because after a reboot it reports the boot that follows. The script now reads the persistent
journal for this boot and the previous one, so it no longer matches the counter that produced
`probe.out`. Neither arm reset and the zero is right for this run, but it is a zero from the weaker
instrument and is worth reading as one.

A program without the probe's self-check would see none of this. It would get zeros, no error, and
a kernel time that looks like a spectacular speedup.
