# The flush-by-scheduler factorial, 2026-08-09


Generated by `scripts/factorial_orchestrate.sh`, which drives `scripts/factorial_battery.sh` once per boot.

Two variables crossed, two boots per cell, run in a mirror-balanced order
(A B C D D C B A) so that drift over the session cannot be mistaken for an
effect. Each numbered directory is one boot; `factorial_results.tsv` is the
summary with one row per boot.

| cell | `flush_pasid_uses_kiq` | `sched_policy` | outcome |
|---|---|---|---|
| A | false (corrected) | default, hardware | clean both boots: probes 3/3, both GEMMs complete, 0 preemption timeouts |
| B | false (corrected) | 2 (software) | probes hang 3/3, both GEMMs wedge, 19 preemption timeouts, queue degraded |
| C | true (stock) | default, hardware | board lost mid-battery on both boots, the KIQ-flush freeze |
| D | true (stock) | 2 (software) | the historical configuration: probes mostly pass, sustained N=4096 wedges or faults |

Only cell A is clean, which is the result the top-level README builds the
working configuration on: the corrected flush removes the freeze that made
hardware scheduling unusable, and hardware scheduling removes the eviction path
that makes compute wedge.

All eight boots here were at 40 CU. A later measurement crossed CU count with
scheduler policy instead and found the wedge tracks the policy at 24 CU as well
as 40, which is in `../kernel-equivalence-2026-08-17/`.

Two boots per cell is thin for a board this variable, so this is the pattern
that held across these boots rather than a settled law.
