# Does the KQV corruption correspond to a different GEMM being dispatched? No, 2026-08-21

Generated by `scripts/kqv_dispatch_trace.sh`.

## Question

Twelve consecutive identical runs of the unpatched build produced nine distinct
perplexities, but with exact repeats: the correct 10.0103 three times and a wrong
115.8450 twice, to four decimals. Accumulated rounding error does not reproduce a
wrong answer exactly, so something appeared to be selecting between a small set
of behaviours, and kernel selection was the obvious candidate.

## Method

Eight unpatched runs at context 2048 with `ROCBLAS_LAYER=2`, logging every
rocBLAS call, then comparing the call signatures of a correct run against wrong
ones. Pointer values are normalised out. The perplexities are the check that the
instrument did not suppress the defect: five of eight came back wrong, so it did
not.

## Result

Every run issues the same work. 448 calls, 8 distinct signatures, in all eight
runs. With the two scalar arguments masked (see below) the signature summaries
are identical across every pair, correct against wrong and correct against
correct alike, while the perplexities are 10.0103, 91.3845, 172.3724 and
1057.5494.

How much of that a reader can check, noted 25 August. Two of the eight signature
files were kept, `sig_2.txt` and `sig_3.txt`, and they are the load-bearing pair:
run 2 is wrong at 91.3845 and run 3 is correct at 10.0103. Masking alpha and beta
makes them identical, which is the comparison the conclusion rests on, and it
reproduces here. "Identical across every pair" cannot be re-derived from what
shipped, because the other six files were not kept.

The harness did not do that comparison either, and its own log says so: it ends
with "correct run: run   wrong run: none" and "cannot compare". The cause is an
off-by-one in two awk field indices, since every log line carries a timestamp, so
the run number was read as the literal word "run" and no wrong run was ever
found. It printed that in every invocation. The comparison reported above was
done by hand afterwards, which is why `masked_signatures.txt` is in this
directory and no `signature_diff.txt` is. The indices are fixed in the harness
now; the finding is unaffected, since the pair that matters is shipped and can be
checked directly.

| run | perplexity | calls | distinct signatures |
|---|---|---|---|
| 1 | 172.3724 | 448 | 8 |
| 2 | 91.3845 | 448 | 8 |
| 3 | 10.0103 | 448 | 8 |
| 4 | 10.0103 | 448 | 8 |
| 5 | 91.3845 | 448 | 8 |
| 6 | 1057.5494 | 448 | 8 |
| 7 | 10.0103 | 448 | 8 |
| 8 | 1057.5494 | 448 | 8 |

So rocBLAS is asked for exactly the same thing every time and does not always
return the same answer. Kernel selection at the library interface is not the
mechanism, and the variation lives below that interface: in how the GEMM
executes, or in data that has already diverged before it is called.

## A trap this run set, and how it was avoided

The first comparison appeared to find the mechanism immediately. The correct run
passed `--alpha 28.125` to the fp16 GEMMs and the wrong run passed
`--alpha -0.0220947`, which looks exactly like a corrupted scalar explaining a
corrupted result.

It is not. Checking alpha against the outcome across all eight runs breaks it:

| run | perplexity | logged f16 alpha |
|---|---|---|
| 1 | 172.3724 | -0.000184059 |
| 2 | 91.3845 | -0.0220947 |
| 3 | 10.0103 | 28.125 |
| 4 | 10.0103 | -2.14062 |
| 5 | 91.3845 | -0.00909424 |
| 6 | 1057.5494 | -1.28906 |
| 7 | 10.0103 | 2800 |
| 8 | 1057.5494 | 62.25 |

The value differs in all eight runs, including the three correct ones, and the
two runs that agree to four decimals on 91.3845 disagree on alpha. A scalar of
2800 actually applied to that GEMM could not produce a correct perplexity. So
the logged scalars are being misread rather than misapplied, most likely the
logging layer printing a half-precision alpha as a float; `beta` behaves the same
way, and the value 28.125 appears as run 3's alpha and run 4's beta, which is
what reading the same uninitialised location twice would look like. Masking both
scalars makes every trace identical.

This is worth recording as an observation about `ROCBLAS_LAYER=2` on this
version rather than about the defect: the alpha and beta printed for fp16
`gemm_batched_ex` calls should not be trusted.

## What it means for the attribution

It weakens the reading that this is purely an upstream fp16 accumulation gap.
That mechanism is deterministic: identical inputs and identical calls should give
identical results, wrong but stable. Here identical calls give four different
answers, which is nondeterministic execution rather than a precision choice, and
nondeterminism points below llama.cpp. What has not been separated is whether the
divergence starts in the GEMM or earlier, since this trace records call shapes
and not data. Capturing the first divergent tensor would settle it and has not
been done.
